# Pre-classroom validation checklist

This project is **not** classroom-ready until every item below is checked off on
your own infrastructure. The table separates what has already been verified from
what only you can verify.

## Verified in development

Environment: Webots R2025a, Ubuntu 24.04, headless (`xvfb`), software rendering.
Evidence: `results/matrix/` and `docs/MEASURED_BOUNDARIES.md`, regenerated by
`python3 tools/run_matrix.py && python3 tools/make_boundary_report.py`.

| # | Item | Result |
|---|---|---|
| V1 | World loads with no errors and no missing PROTO | Pass |
| V2 | Supervisor, controller and Robot Window plugin all resolve | Pass — no "robot window library has not been found" warning |
| V3 | Robot Window renders and drives the whole flow | Pass — form, requirement list, verdict, per-requirement checks, live telemetry, test log, CSV export all exercised in a headless browser |
| V4 | Run and Reset produce **isolated** executions | Pass — a case run alone and the same case run after two unrelated cases produced bit-identical measurements |
| V5 | Repeated runs are **repeatable** | Pass — verdict and all discrete outcomes exact; completion time exact; clearance within 0.0002 m and path length within 0.0016 m over a 90 s cluttered run |
| V6 | Pass/Fail is correct for known scenarios | Pass — 49-case matrix, 25 pass / 18 fail / 10 rejected, each with a stated reason; clearance figures cross-checkable by hand from the arena geometry |
| V7 | Parameter space contains meaningful passing **and** failing cases | Pass — boundaries measured on four independent axes |
| V8 | Out-of-range and malformed input is rejected without running a test | Pass — 10 rejection cases including non-numeric, out-of-range, unknown scenario, unknown parameter, fractional integer, degenerate start/goal |
| V9 | Startup and run time are acceptable | Pass — 49 cases in ≈ 90 s headless; a single 30 s student run is a few seconds of wall clock |
| V10 | Version pinning is consistent | Pass — `#VRML_SIM R2025a utf8` and the vendored `RobotWindow.js` (copied from the Webots tree at tag `R2025a`, checksums in `plugins/robot_windows/test_lab/VENDORED.md`) agree |

## You must verify — students installing Webots locally

This is the supported path for the assignment, documented in [SETUP.md](SETUP.md).
It has no server, no account and no network dependency, which is exactly why it
is the one to validate first.

**L1 is new and unverified.** The robot window used to import `RobotWindow.js`
over the network from cyberbotics.com; it now imports two vendored copies
sitting beside `test_lab.html`. The files are byte-identical to upstream R2025a
and the import is a plain relative path, but nobody has yet opened the window in
desktop Webots since the change. Check it before anything else.

| # | Item | How to check |
|---|---|---|
| L1 | The robot window loads with the vendored `RobotWindow.js` | Open the world in desktop Webots R2025a, *Show Robot Window*, confirm the status badge leaves "Connecting…" and a run completes. Then **turn the network off and do it again** — that is the property the vendoring buys. |
| L2 | [SETUP.md](SETUP.md) works on a clean machine | Follow it start to finish on each platform students will actually bring: Windows 11, Apple Silicon macOS, Intel macOS. A machine that already has Webots on it proves nothing. |
| L3 | The three self-check runs give the documented results **in the GUI** | The expected values in SETUP.md step 7 were measured headlessly. Confirm the GUI agrees, in particular the ≈ 19.7 s completion time; loosen the wording in SETUP.md if it drifts. |
| L4 | The Python-command fix is sufficient on a clean macOS | Webots defaults to `python`, which most Macs do not have. Confirm that setting **Python command** to `python3` is enough, and record the absolute path that works if it is not. |
| L5 | The ZIP download path works, not just a `git clone` | Download the ZIP from GitHub, unzip, open the world from the `webots-testing-lab-main` folder. Relative controller and robot-window paths must still resolve. |
| L7 | Nothing here has ever been run in the **desktop** Webots GUI | V1-V10 were all established headlessly on Ubuntu, and V3 exercised the robot window in a headless browser rather than in Webots itself. The desktop path is now the supported one for students, so it needs its own first run. L1 is the narrow version of this; this row is the whole of it. |
| L8 | The class's actual hardware can run Webots | R2025a supports macOS 12-14 officially and says nothing about newer; it advises against Intel integrated graphics. Survey the class early — one question about laptop model and OS version — rather than discovering the distribution during the lab session. |
| L6 | A student can get from nothing to a passing run inside the stated budget | Time one student who has never seen it. SETUP.md claims 30 minutes; if it takes 90, say 90. |

## You must verify — the webots.cloud path

These depend on your Docker Hub access, your GitHub repository, the SJSU network
and the public webots.cloud servers. None of them can be established from a
local run, and a successful local run is not evidence for any of them.

Check C0 first, because it can make the rest moot: as of the last check, the
public simulation-server pool was **empty**, and `webots.cloud/ajax/server/session.php`
answered *no simulation server available at the moment* for every world,
including Cyberbotics' own demonstrations. Treat this path as a bonus, not as
the delivery mechanism, until C0 passes.

| # | Item | How to check |
|---|---|---|
| C0 | webots.cloud has any simulation server at all | <https://webots.cloud/server> lists at least one, and a known-good official demo actually starts. If neither, nothing below is testable and nothing you change in this repository will help. |
| C1 | The default webots.cloud image opens an R2025a world | There is no `Dockerfile`, so webots.cloud uses its own default image. Confirm the simulation loads; if it complains about the world version, add a pinned `Dockerfile` per [DOCKER_IMAGE.md](DOCKER_IMAGE.md). |
| C2 | The repository is registered and the world is published | Push to a **public** GitHub repo, then on <https://webots.cloud/simulation> press *Add a new simulation* and paste the blob URL of the world file including the branch name. webots.cloud requires R2022b or newer; this world is R2025a. |
| C3 | **The project opens without a student login** | Open the run link in a private/incognito window with no webots.cloud session. |
| C4 | The 3D simulation starts in current Chrome | Open the link, confirm the robot moves and the scene renders. |
| C5 | The 3D simulation starts in current Edge | As above. |
| C6 | The 3D simulation starts in Safari where applicable | As above, on macOS/iPadOS if students will use them. |
| C7 | Robot Window controls change the intended parameters | Set corridor width 0.20 and again 0.80 and confirm the barrier gap visibly changes; set start heading 180 and confirm the robot starts facing away. |
| C8 | Run and Reset behave in the browser as they do headlessly | Run the same case twice in one browser session and confirm identical verdicts; press Reset and confirm the arena returns to its initial state. |
| C9 | It works **on the SJSU network** | Test from campus wifi and from the lab machines, not only from home. WebSockets to webots.cloud must not be blocked. |
| C10 | Concurrent sessions work at expected class size | Have the real number of students open the link simultaneously. The capacity of the public webots.cloud simulation servers is not documented; assume nothing. |
| C11 | Simulation start-up time and failure rate are acceptable under that load | Measure time-to-first-frame with the class connected, and count sessions that fail to start. |
| C12 | Students' downloaded CSVs open in whatever they will write reports in | One student's export, opened in Excel and in Sheets. |

## If concurrency does not hold up

C10 is the item most likely to fail, and it is the one that decides whether this
delivery method works at all. In rough order of effort:

1. **Stagger access.** Split the class into groups by lab section or half-hour
   slot. Costs nothing and often suffices.
2. **Host a Webots simulation server on SJSU infrastructure.** The same
   repository works; only the server URL changes. This is the recommended
   fallback if the department can provide a host.
3. **Run locally.** Webots installed on the student's own laptop or on lab
   machines, this repository downloaded, `webots worlds/sw_testing_lab.wbt`.
   Loses the no-install property but nothing else — the Robot Window, the
   oracle and every measured boundary are identical. This is what
   [SETUP.md](SETUP.md) documents, and while C0 fails it is not a fallback but
   the primary path.
4. **Build a smaller purpose-built browser simulator.** Full control, but the
   physics, the sensor model and the oracle all have to be rebuilt and
   revalidated. Only worth it if the lab becomes a permanent fixture.

Options 1 to 3 keep this project intact. Only option 4 discards it.

## Re-run after any change

```bash
python3 tools/run_matrix.py --out results/matrix   # exits non-zero on regression
python3 tools/make_boundary_report.py              # refresh the documented numbers
```

Both should be part of whatever CI you point at this repository. The runner's
exit status is meaningful: it fails if the parameter space stops containing both
outcomes, if input rejection stops working, or if repeated runs stop agreeing.
